# 产品需求与 PRD 规范

**文件编号**：PD-2026-008　**发布部门**：产品设计部　**生效日期**：2026-03-01　**版本**：2026-09
**适用范围**：产品经理、设计师、研发与测试人员

## 一、需求来源与优先级

1. 需求来源包括：客户反馈、销售线索、数据洞察、战略规划、线上问题。
2. 优先级定义：

| 优先级 | 定义 | 响应要求 |
|--------|------|---------|
| P0 | 线上故障、核心流程不可用、合规风险 | 24 小时内响应并给出方案 |
| P1 | 影响主要客户使用、有明确商业价值 | 当个迭代（2 周）内排期 |
| P2 | 体验优化、效率提升 | 进入需求池，按季度评估 |
| P3 | 长期规划、探索性需求 | 每季度回顾一次 |

3. 需求必须写明**业务价值与衡量指标**，无法说明价值的需求不予排期。

## 二、PRD 必备章节

一份合格的 PRD 必须包含以下章节，缺一不可：

1. **背景与目标**：现状问题、业务目标、成功指标（可量化）。
2. **用户与场景**：目标用户角色、使用场景、典型任务流程。
3. **功能清单**：功能点、优先级、是否本期实现。
4. **交互说明**：主流程、异常流程、边界情况（空态、加载态、错误态）。
5. **数据与字段**：新增或变更的数据结构、字段含义、校验规则。
6. **权限与角色**：哪些角色可见、可操作，越权时的表现。
7. **埋点方案**：事件名称、触发时机、上报字段。
8. **验收标准**：测试可逐条验证的清单。

## 三、需求评审

1. 评审时间：每周**周二、周四**下午，产品经理提前 1 个工作日发出 PRD 与原型。
2. 参会人：产品、设计、研发负责人、测试；涉及数据或权限的须邀请对应负责人。
3. 评审结论分为：通过、有条件通过（需补充材料）、退回。评审结论与遗留问题记录在需求单中。
4. 评审通过后需求进入开发；开发过程中需求变更须重新评审，禁止口头变更。

## 四、埋点规范

1. 事件命名格式：**模块_动作_对象**，例如 kb_upload_document、chat_send_message。
2. 属性命名使用小写下划线，禁止使用中文属性名。
3. 新增埋点须在 PRD 中列出完整的事件与属性清单，由数据分析同学确认后再开发。

## 五、上线与复盘

1. 功能上线后，产品经理须在 2 周内输出数据复盘：目标达成情况、用户反馈、后续动作。
2. 未达预期指标的功能，须明确「优化 / 下线 / 保留观察」的结论。

## 六、文档管理

PRD、原型、评审记录统一存放于产品知识库，命名格式为「项目名-版本号-文档类型」。历史版本保留，不得覆盖。
