# server-py/evals —— 关键模块评测集

这套评测集只做一件事：**用真实接口、真实公司文档、真实模型调用，把关键模块的行为钉住**，
让"改了 A 模块、B 模块悄悄坏了"这种事在合并前就暴露出来。

- 不 mock：每一条用例都打真实 HTTP 接口（`/api/knowledge/search`、`/api/chat/stream`、
  `/api/agent/run`、`/api/erp/parse`），因为要测的正是"权限、检索、路由、结构化输出"
  这一整条链路，mock 掉任何一段，通过率都不再说明线上可用。
- 不放宽：判定不过就是不过。失败明细会打印"期望 vs 实际"，README 里维护"已知失败项 + 原因"。
- 不断言实现细节：只断言用户能感知的东西（命中了哪篇文档、回答里有没有这条结论、
  调用了哪些工具、表单字段对不对），这样重构内部实现不会让评测无谓地红。

## 一、目录与文件

| 路径 | 作用 |
|------|------|
| `datasets/rag_retrieval.json` | RAG 检索召回（10 条）：Recall@k、命中切片的正文结论、权限过滤、检索范围收窄 |
| `datasets/intent.json` | 意图判定（6 条）：该不该查知识库（needKnowledge） |
| `datasets/answer_grounding.json` | 回答落地性（8 条）：要点必须出现在回答里；库里没有的必须明说没查到 |
| `datasets/agent_tasks.json` | 任务 Agent（6 条）：工具调用、路由分支、最终回答要点、流式输出完整性 |
| `datasets/erp_parse.json` | ERP 智能填单（5 条）：自然语言 → 结构化表单字段逐项比对 |
| `run_evals.py` | runner（纯标准库：urllib + json + argparse + concurrent.futures） |
| `reports/` | 每次运行的 JSON + Markdown 报告（自动生成，带时间戳） |

每条用例都有一个 `guard` 字段，写清楚**这条在防什么回归**；报告里会原样带出来，
所以失败时不用回去翻数据集就知道它意味着什么。

## 二、怎么跑

### 一键（推荐）

```bash
# WSL / Linux / macOS 里，仓库根目录执行
bash scripts/run-evals.sh                      # 跑全部 5 个集
bash scripts/run-evals.sh --suite intent --verbose
bash scripts/run-evals.sh --limit 3 --suite rag_retrieval   # 调试：每个集只跑前 3 条
API_BASE=http://127.0.0.1:3000 bash scripts/run-evals.sh
```

脚本会先做两道前置检查，避免跑出一片没有诊断价值的红：

1. `/health/live` 必须通（进程活着）；
2. 真发一次对话流，必须吐出 token —— 进程健康但模型链路坏了（Key 失效、依赖版本改动、
   结构化输出改动）时，评测只会得到一片 500，那种红说明不了模块问题。

确认无关时可以用 `FORCE=1` 跳过第 2 道检查。宿主机没有 python3 时，脚本会自动
把 `evals/` 复制进 `workmind-server` 容器里跑，并把报告复制回仓库。

### 直接跑 runner

```bash
cd server-py/evals
python run_evals.py [--suite rag_retrieval] [--base-url http://127.0.0.1:3000] [--out report.json] [--verbose]
```

| 参数 | 说明 |
|------|------|
| `--suite NAME` | 只跑指定评测集，可重复；名字见上表（默认全部） |
| `--base-url` | 服务地址，默认 `http://127.0.0.1:3000` |
| `--out` | JSON 报告路径（Markdown 报告同名同目录）；默认写 `reports/eval-report-<时间戳>.json` |
| `--limit N` | 每个集只跑前 N 条（调试用） |
| `--top-k N` | 检索评测的 TopK（默认按用例里的 k，缺省 6）。要出「Top5 召回率」就 `--top-k 5` |
| `--case ID` | 只跑指定用例 id，可重复；复盘某条失败用例用（例如 `--case agent-004`，用来判断"是稳定失败还是偶发"） |
| `--concurrency N` | 并发数，默认 1。对话/Agent/ERP 接口都有令牌桶限流（容量 30 / 每秒补 10），并发高了会撞 429 |
| `--verbose` | 逐条打印通过/失败与"期望 vs 实际" |
| `--tenant-id / --user-id / --departments / --clearance` | 换评测身份（默认见下） |

退出码：**有失败用例就返回非 0**，方便接进 CI 或"合并前拦一道"。

> ⚠️ **评测请求都带 `noCache: true`**（后端会跳过答案缓存的读与写）。
> 这不是可选项：缓存命中时后端直接重放答案，既不发 `intent` 事件也不发 `sources` 事件，
> 评测会把"重放"当成模型输出 —— 2026-09-30 实测，一轮 35 条里有 6 条因此误判失败
> （5 条"引用越界"假失败 + 1 条"未收到 intent 事件"）。指标要可信，就必须打真实模型。

## 二·五、离线指标汇总（七个指标一张表）

```bash
python run_evals.py --top-k 5        # ① 先出一份 Top5 口径的评测报告
python offline_metrics.py            # ② 汇总（读最新报告 + 监控看板 + trace + ERP 申请）
python offline_metrics.py --report reports/eval-report-xxx.json --out reports/offline-metrics.md
```

`offline_metrics.py` 把评测结果与运行期数据（落库的 `usage_calls` / `trace_runs` / ERP 申请）
拼成一张表，**每个指标都写明口径与样本量**，方便对外讲、也方便别人复算：

| 指标 | 口径 | 数据来源 |
|------|------|---------|
| Top5 召回率 | 每条检索用例 `recall_at_k` 取平均 | 评测报告 |
| 答案准确率 | 回答要点必须真的出现 + 不得编造公司规定 | 评测报告 |
| 引用准确率 | 回答里的 `[n]` 与 `sources` 对得上的比例；越界编号 / 本轮无来源却标引用 → 该用例失败 | 评测报告 `citationPrecision` |
| P95 延迟 | 评测逐条耗时 P95；另给监控看板排除缓存后的 P50/P90/P99 | 评测报告 + `/api/monitor/stats` |
| Token 成本降幅 | 缓存命中省下的 token ÷（实际消耗 + 省下），近 7 天窗口 | `usage_calls` |
| 任务成功率 | Agent 任务评测通过率；另给运行期 trace 成功率 | 评测报告 + `/api/trace/stats` |
| 人工介入率 | 审批链被 `need_info` 打断的申请占比 | `/api/erp/applications` |

引用准确率只判"**错得明确**"的两种：编号越界（写了 [5] 但只有 2 条来源）、
本轮没有任何来源却标引用（编造出处）。**不**做"引用的那一片是否真的支撑这句话"的语义比对——
模型常做同义改写，关键词比对会大量误判，那种指标没人敢信；语义级核查留给人工抽查。

### 评测身份（很关键）

默认身份是 `tenant-demo / u-tech-01 / tech / internal`，也就是"技术研发部 + 内部密级"。
这个身份**看不到** hr / finance / legal 的部门文档，而 general 制度文档都看得到，
所以"越权召回"和"过度过滤"两类回归都能被同一次运行抓住。

四个身份头（`X-Tenant-Id` / `X-User-Id` / `X-User-Departments` / `X-User-Clearance`）
由 runner 统一带上；漏带会落到 anonymous/public 身份上，表现成"检索全 0 条"，
排查方向会被带偏到权限上 —— 所以 runner 里把这四个头写成了一个函数，不散落在各用例里。

前置数据（`bash scripts/seed-knowledge-base.sh`）需要先灌好 10 篇公司文档，否则检索类用例会整体失败。

## 三、每个集在测什么、怎么判定

### 1. rag_retrieval（10 条）—— 检索召回

打 `POST /api/knowledge/search`，一条用例判定三件事：

1. **Recall@k**：`expect_docs` 里的文档标题至少要有 `min_hits`（默认 1）份出现在 TopK 里（标题子串匹配）；
2. **正文结论**：命中切片的 `content` 里必须出现 `expect_keywords` —— 只比标题会漏掉
   "召回到了文档、但答案那一片没被召回"这种最坑的情况（同一份制度在第二章讲住宿、第三章讲餐补）；
3. **不得出现**：`forbidden_docs` 里的文档一条都不能出现。

覆盖四类用例：常识型制度问答（年假/差旅/报销/员工手册）、技术规范、**权限过滤**
（tech 身份问考勤/合同/财务必须召不回）、**检索范围收窄**（`department` 硬过滤、`docType` 收窄）。

统计口径：每条用例记 `recall_at_k = 命中期望文档数 / 期望文档总数`，报告里同时给出命中条数、
`recall.reason`（`ok` / `below_threshold` / `rerank_rejected` / `all_filtered`）与最高分，
所以"为什么没召回"在报告里就能看出来，不用再去翻日志。

### 2. intent（6 条）—— 该不该查知识库

打 `POST /api/chat/stream`，**只读到 `intent` 事件就断开**（intent 事件在检索与模型调用之前
就已经下发，读完就能判定，省掉等待整段回答生成的时间）。判定 `needKnowledge` 是否符合预期，
可选再钉一下 `decisionSource` 前缀（`skip-*` / `recall-first`）。

覆盖两类：**该跳过的**（打招呼、客套话、自我介绍、闲聊创作、翻译、写作生成、日期、纯算式、天气）
和**该查库的**（制度提问、口语化制度提问、短问句、部门专属知识），
其中 `rag召回失败怎么办` 是 README 里记录过的历史回归（旧 strict 模式会判"不需要检索"）。

### 3. answer_grounding（8 条）—— 回答落地性

打 `POST /api/chat/stream`，把 `token` 事件拼成回答后判定：

- `must_include`：全部要点都要出现（金额、天数、比例这类硬事实）；
- `must_include_any`：每组至少命中一个说法（同一件事的多种表述，避免判定过严）；
- `not_in_kb: true`：回答里**必须**出现「知识库中没有查到相关内容」或「知识库中未找到相关内容」。
  这类用例问的是库里确实没有、或当前身份看不到的内容（合同规范是 confidential、
  年会安排压根没写进制度），防的是"编一条公司规定出来"。

判定前会做一次**归一化**：去掉空白和 Markdown 强调符号，再比子串 ——
模型把"600 元"写成"600元"或"**600 元**"不算事实缺失（排版一致不是这条用例要测的东西）。

### 4. agent_tasks（6 条）—— 任务 Agent

打 `POST /api/agent/run`（SSE），比对：

- `expect_route`：走的是 knowledge / tool / chat 哪条分支；
- `expect_tools` / `forbid_tools`：真实调用了哪些工具（`tool_call` 事件里的 `toolName`）；
- `answer_keywords` / `answer_any` / `forbid_answer_phrases`：**最终回答**里必须/不得出现的内容；
- `forbid_token_duplication`：流式输出完整性。

两个容易搞错的判定细节：

1. **最终回答只取 `answer_reset` 之后的 token**。Agent 在决定调工具前吐的那些字（"我先查一下…"）
   是过程说明，前端收到 `answer_reset` 会把它挪到灰色过程区；如果评测把过程说明也算进回答，
   关键词命中就会**假通过**（过程里提到"年假 15 天"，最终回答其实没写）。
2. **按 token 事件检测"重复发送"**，而不是按文本猜叠字：正常中文本来就有"谢谢/刚刚"这类叠词，
   而重复发送时 token 一定成对出现（`"公司","公司","年","年"`），
   非空 token 的相邻重复率在故障时 ≈0.5、正常对话流 ≈0，阈值取 0.3 两边都不擦边。
   这个指标每条 Agent 用例都会记录（`metrics.tokenDuplication`），报告里能看到。

### 5. erp_parse（5 条）—— 自然语言 → 结构化表单

打 `POST /api/erp/parse`，逐字段比对：`type`（费用/假期类型）、`totalAmount`（**按文本里的
算术期望值精确比对，±0.01 容差**）、`itemsMin`、`itemNamesAny`、`startDate`/`endDate`、
`days`/`workdays`、`reasonContains`、`warningsAny`。

两条出题纪律：

- **只用绝对日期**（2026-03-13 而不是"下周五"），否则用例会随时间漂移，今天过明天挂；
- **金额期望值自己算清楚**（写进 `guard` 里，例如 1740+1200+450+260=3650），
  这样"模型算错钱"和"评测写错期望"能分清。

### agent-004 的抖动：已定位并修掉（不再是已知失败项）

首轮评测发现 `agent-004`（查年假政策 + 算剩余天数 + 通知 HR）会抖：
三次完整运行里 `agent_tasks` 分别是 10/11、11/12、12/12，失败时**路由判成了 knowledge**，
于是「计算」和「通知」两步整段消失（回答只有政策那一段，既没有"9 天"也没有通知）。

根因不是模型抽风，而是**这条策略本身不成立**：知识分支（`knowledge_answer`）只会"读文档 + 回答"，
它做不到算数、也做不到发通知 —— 把决定权完全交给模型判一次，就必然有概率丢掉这两步。

修法（`app/services/agent/agent.py`）：给路由加一个**确定性硬信号**
`_tool_capability_need(task)` —— 任务里一旦出现「计算/通知/报告」这类诉求
（关键词刻意取得偏保守：用「计算一下」而不是「计算」，避免"餐费标准怎么计算？"这种纯提问被误判），
就直接走工具分支，不再只看模型怎么判。理由写在代码注释里：
**知识分支做不到的能力，不该由模型决定"要不要做"**。

修复后同一用例连跑 3 次：**3/3 通过**（此前 3 次里失败 2 次）；全量评测两次都是 69/69。

```bash
python run_evals.py --suite agent_tasks --case agent-004 --verbose
```

历史完整报告（含失败样本）都留在 `reports/` 里，可以对照同一个用例在不同时间的表现。

### 一处判定口径的修正（如实说明）

首轮全量运行有 2 条失败（`agent-002`、`agent-005`），但**回答本身是对的**：
模型把金额写成财务习惯的千分位形式（`3,390 元`、`2,400 元`），而用例期望的是 `3390` / `2400`。
这属于排版差异、不是事实缺失，所以把 runner 的 `norm()` 补上了"去掉数字内部千分位逗号"
（`(?<=\d),(?=\d{3})`，只动数字之间的逗号，不会把"1740, 1200"粘成一个数）。
**除此之外没有放宽任何判定**：要点缺失、工具没调用、路由走错分支，一律照旧算失败。

## 五、已知失败项与原因

### 1. agent-004：路由抖动导致"任务只做一半"（**已修复**，保留记录）

这条用例最初被如实记为失败（3 次里错 2 次），**判定没有被放宽**：
任务里明确要求"计算剩余天数"和"通知 HR"，两个工具一个都没调用就是没完成。

修复方式是改产品代码（给路由加确定性硬信号，见上一节），而不是改判定。
修复后连跑 3 次全部通过。**这条用例留着**：以后谁把那个硬信号删掉，它会立刻变红。

### 2. 评测期间发现并已修复的三个回归（保留记录，说明评测集确实在拦东西）

| 现象 | 评测里的证据 | 根因 / 处置 |
|------|-------------|------------|
| Agent 流式输出**每个 token 连发两遍**（用户看到"公公司司年年假假"） | `agent_tasks` 的 `metrics.tokenDuplication` ≈ **0.50**（对话流同时为 0），最终回答拼接后全是叠字 | 模型韧性外壳被写成 `BaseChatModel` 子类，"模型里再包模型"导致内外两次都发 `on_chat_model_stream`。已改为普通 Runnable。现在由 **agent-012** 这条用例专门守着 |
| `POST /api/erp/parse` **100% 返回 500**；Agent 任务路由器**静默降级**成"永远走工具分支" | `erp_parse` 10/10 全红（`HTTP 500`）；Agent 日志反复出现 `classify failed, fallback to tool`（纯知识任务被判成工具分支），`agent-008` 的 `route=knowledge` 断言随之失败 | 韧性包装的 `_delegate(self, method, ...)` 与 `with_structured_output(..., method="function_calling")` 撞名（`got multiple values for argument 'method'`）。已把委托参数改成位置限定名 `op`，并给"路由失败"补了 error 级全链路追踪（不再静默） |
| **检索明明命中，回答却说"知识库中没有查到相关内容"**（潜在缺陷，当前未触发） | 走工具分支且知识库有预检索命中时，后端把 `miss_notice` 误置位，回答以"没查到"开头再自我纠正 | 代码路径：`run_agent` 里 `pre_sources` 被清空**之后**才计算 `kb_missed`。已在 **agent-005** 上加了 `forbid_answer_phrases` 断言，一旦路由走到工具分支就会被抓出来 |

### 3. 关于"服务不可用"这类失败

后端容器被并发改动/重启时，评测会因为连接被拒而失败。报告里把这种失败单独统计成
`infraFailed`（失败明细带 `[服务不可用]` 前缀），不当作模块回归 —— 但**不会自动重试到通过**：
runner 只对连接级错误做几次退避重试（约 30 秒），仍失败就如实记为失败。

## 六、加用例时的注意事项

1. **基于真实文档出题**：期望值必须能在 `docs/company/*.md` 里逐字找到（或按文本算术推出来）。
   凭印象编一条"公司年假 10 天"这种用例，只会让评测自己变成本身的 bug。
2. **能自动判定**：每条用例都要能被 runner 判定出通过/失败 —— 需要人读一遍才知道对不对的用例，
   不要放进来（放进来也只会长期被忽略）。
3. **写清楚 guard**：一句话说明"这条在防什么回归"。没有 guard 的用例，失败时没人知道要不要管。
4. **注意身份可见性**：出题前先确认这个文档在当前身份下可见（见 README 的可见性表），
   否则会把"权限正确"误判成"检索坏了"。
5. **避免相对日期**：ERP 与 Agent 用例里的日期一律写绝对日期。
6. **失败就让它失败**：判定不过的用例要保留并写进 README 的"已知失败项"，
   不要为了数字好看删用例或放宽判定 —— 那等于把报警器拆了。
